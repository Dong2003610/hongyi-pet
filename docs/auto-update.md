# 桌宠一键更新

Windows x64 便携版从 **1.1.0** 开始支持应用内更新。旧版没有更新入口，需要先退出旧桌宠，手动解压 1.1.0 到独立文件夹并打开一次。后续只需打开小屋的设置，点击「下载并重启」。请保持程序名称为「小红桌宠.exe」。

## 日常使用

- 启动约 10 秒后检查正式版本，之后每 6 小时检查一次；失败后约 15 分钟重试。桌宠需要正在运行且能够联网。
- 发现新版会在小屋显示更新按钮，并通过头顶气泡、开心动作、提醒音和系统通知提示。每个版本只自动提醒一次，专注和安静时段结束后再提示；音效沿用现有声音开关。
- 设置中的「自动检查新版本」可以关闭；手动「检查更新」仍可用。自动检查只提示，安装始终需要点击。
- 默认优先使用 `ghfast.top` 下载镜像，失败后尝试 GitHub。可以在更新设置中关闭镜像。镜像同步可能有延迟。
- 1.1.1 起，版本检测优先读取 GitHub 公开版本 API；下载镜像失败时可通过 GitHub 资产 API 获取。API 不可用时仍尝试正式版本清单。所有路线保持 HTTPS 和大小、SHA-256 校验，不需要用户配置 GitHub 密钥。
- 点击「下载并重启」后显示下载进度，下载期间可以取消。下载和准备失败时保留当前程序，可以重试。
- 更新前暂停并保存专注计时；更新后可手动继续计时。设置、AI 配置、登录、聊天、任务回执等保存在 Electron 原有的用户数据目录，不参与程序目录替换。

请将桌宠放在独立、可写的程序文件夹中，不要直接解压到桌面根目录、下载根目录或用户目录。更新会整体替换这个程序文件夹，其中自行放入的其他文件也会随旧版进入备份。

## 替换与恢复

更新包按正式版本清单验证大小和 SHA-256，解压时校验路径，准备完成后才退出旧版。后台助手等待旧进程退出，再将新程序换入原路径并启动。新版只有在三个窗口及人物素材加载成功后才确认启动健康；45 秒内没有确认则尝试恢复并启动旧版。

程序目录旁会保留 `.hongyi-backup-<更新编号>` 旧版备份；用户数据目录的 `updates/<更新编号>/` 保存下载包和结果。如果无法自动恢复，界面会提示结果文件位置。备份和更新记录目前不会自动清理，确认新版正常后可手动删除不需要的旧备份和已完成下载记录，避免长期占用磁盘。不要在更新过程中删除这些目录。

这是进程级启动检查与回滚。断电、磁盘故障或防护软件持续锁定文件时仍可能需要手动恢复；可退出桌宠，将对应备份目录恢复为原程序文件夹。保留的数据目录无需改动。SHA-256 用于验证下载完整性，当前版本没有额外的代码签名。

## 后续发布流程

**正常使用只需把改动推送到 main，不再需要手动递增版本或创建标签。** GitHub Actions 会自动完成：

1. 比较当前源码版本和已经正式发布的版本；如果仍是旧版本，自动递增补丁号，例如 `1.1.1 → 1.1.2`。如果已经手动指定更高版本，则沿用指定版本。
2. 同步 package、锁文件和两份 pet-spec，记录受保护文件迁移，并从提交记录生成更新说明。
3. 运行类型、全部单元、Windows 替换回滚和网络传输测试，再打包并校验 ZIP。
4. 检查 main 没有被后来的提交推进，将版本记录和标签原子推送，再上传更新包和清单。两个文件上传完成后才把草稿发布为最新正式版本。

同一时间只运行一个发布流程；main 在构建期间有新提交时，本轮不会覆盖它，由后续构建发布完整的新改动。测试或打包失败不会发布。版本提交使用 GitHub Actions 身份和 `[skip ci]`，避免循环构建。已发布版本不覆盖，所有新改动使用新版本号。

如果在提交版本后遇到 GitHub 上传故障，可在 Actions 的 build 工作流对 main 执行 Run workflow；它会沿用尚未发布的版本并继续发布。不要只重跑一个已经落后于 main 的旧提交。`main` 需要允许该仓库 Actions 的 `contents: write` 权限，分支保护禁止机器人提交时流程会明确失败，不会绕过保护。

桌宠仍读取 **GitHub Releases 最新正式版本**及相应的 `update-manifest.json`，下载 `hongyi-pet-win32-x64-v<版本>.zip`；开发模式、测试模式和其他平台不执行替换。仅上传到其他分支或 Actions artifact 不会向用户发布。需要指定较大版本时，也可提前运行 `node tools/prepare-version.mjs 1.2.0`。手动版本标签构建继续兼容。

本地构建使用 `npm run portable:win`，然后运行 `node tools/prepare-update-release.mjs` 生成上传资产。构建收集器会重建输出目录，应在隔离的源码暂存目录中构建，保留正在使用的便携版。

如果使用本机构建资产发布，可先通过现有 `tools/publish-contents.mjs` 同步并验证源码，再用 `node --use-system-ca tools/publish-update-release.mjs <更新包目录>` 预检。核对远端提交后设置 `EXPECTED_HEAD` 并加 `--apply`：脚本先建立草稿，上传并核对 GitHub 返回的 SHA-256，再将完整版本设为正式发布；失败时保留草稿，不替换已经发布的同版本资产。发布工具只使用本机 Git 凭据管理器，客户端更新无需 GitHub 密钥。

回归覆盖版本比较、镜像回退、下载校验、取消、状态通知、设置持久化、IPC 权限、真实 Windows 文件夹替换与回滚、中文及特殊字符路径，以及真实便携版的启动健康确认。测试使用隔离账号数据和本地模拟服务，不连接真实任务账号或付费 AI。
